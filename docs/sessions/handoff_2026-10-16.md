## A. codex 세션이 sync 마다 다시 처리되는 문제 (PR #1)

### 발견

사용자가 증상을 제보했어요. 원문은 다음과 같아요.

> 이게 버그인지 모르겠는데 이미지 생성처럼 턴이 짧은 codex 대화가 들어가 있으면 다 처리도 안되고 반복해서 처리하고 있는거 같아. 거기에다가 오래걸려서 제대로 처리가 안되는지 훅 걸어놨던 secall 상태메시지도 나타나지 않을정도야. 아마 훅은 걸렸는데 secall sync --local-only --no-wiki가 너무 오래걸려서 종료되는거 같기도 하고 그래

### 탐색

1. Claude는 직전 커밋 `b80eeb3`(초단문 턴을 벡터 인덱스에서 제외하는 `MIN_CHUNK_CHARS`)을 `git show`로 먼저 열었어요. 가설은 이랬어요. 턴이 모두 짧으면 청크가 0개가 된다. 그러면 "아직 임베딩 안 됨"으로 판단해서 매번 다시 임베딩한다.
2. Grep으로 `chunk_session|sessions_without_vectors|find_sessions_without|not_embedded|unembedded|without_vector`를 찾았어요. 그리고 `crates/secall-core/src/store/vector_repo.rs:359`(`find_sessions_without_vectors`), `crates/secall-core/src/search/vector.rs:89`(`has_pending_chunks`), `crates/secall/src/commands/embed.rs`를 읽었어요.
3. **헛짚은 곳:** `has_pending_chunks`는 청크가 0개이면 `false`를 반환해요(`vector.rs:96`). 그래서 짧은 세션을 건너뛰어요. `find_sessions_without_vectors`는 `lint.rs:215`만 호출하고, sync는 이 함수를 쓰지 않아요. 짧은 턴 가설은 여기서 버렸어요.
4. 그다음 sync 경로를 따라갔어요. `crates/secall/src/commands/sync.rs`에서 `run_auto_ingest`(`sync.rs:536`)를 찾았어요. 그 함수는 `ingest_sessions`(`crates/secall/src/commands/ingest.rs:370`)를 호출하고, 그 안에서 `ingest_path`가 중복을 검사해요(`ingest.rs:665-697`).
5. 중복 검사에서 `db.is_session_open()`이 true이면 `delete_session_full` 후 재인제스트하는 분기를 찾았어요(`ingest.rs:672-685`).
6. Grep으로 `end_time`을 codex 파서에서 찾았어요. `crates/secall-core/src/ingest/codex.rs:284`가 `end_time: None`을 고정으로 넣었어요. `is_session_open`은 `end_time IS NULL`로 판정해요(`crates/secall-core/src/store/session_repo.rs:149`).
7. sqlite3 CLI가 없어서 `python -I`의 `sqlite3` 모듈로 `%LOCALAPPDATA%\secall\index.sqlite`를 읽기 전용으로 조회했어요. 결과는 codex 429개 중 429개, claude-code 151개 중 0개가 `end_time` NULL이었어요.
8. 영향 범위를 확인했어요. `delete_session_full`(`session_repo.rs:341`)은 벡터와 그래프까지 지워요. 재인제스트한 세션은 `new_session_ids`에 들어가요(`ingest.rs:1222`). 그래서 시맨틱 엣지 추출(LLM)도 매번 다시 해요.
9. 다른 파서와 비교했어요. `claude.rs:323`은 `end_time = last_timestamp`이고, `gemini.rs:260`도 `end_time`을 채워요.

### 분석

codex 파서가 `end_time`을 항상 NULL로 저장했어요. ingest는 NULL을 "진행 중인 세션"으로 해석해요. 그래서 sync가 실행될 때마다 codex 세션 429개를 모두 지우고 다시 처리했어요. 이 처리는 파싱, BM25 인덱싱, 전체 청크 임베딩, LLM 시맨틱 추출을 포함해요. sync가 훅 시간 제한 안에 끝나지 않았고, 훅이 종료되면서 상태 메시지도 나오지 않았어요. 다음 sync는 다시 처음부터 시작했어요.
최근 이미지 생성 세션(`s1`, `sprite-gen-*`)이 늘어서 증상이 더 잘 보였어요. 짧은 턴 자체는 원인이 아니에요.

Claude는 2026-09-07 session2 핸드오프의 결론도 언급했어요. 그 문서는 "Orca 유령 세션 141개를 매번 임베딩"한 것을 원인으로 봤어요. 이 버그도 그 증상의 일부였을 가능성이 높아요. 이 판단은 **미검증**이에요.

## B. DB 중복 검사와 vault 파일명 충돌 (PR #2)

### 발견

사용자가 물었어요: *"정상적으로 다 처리 된거 같아. 그런데 이전에 여러번 실행한것들은 db에 중복으로 저장된건 아닌지 궁금해."*

### 탐색

1. `sqlite_master`로 스키마를 확인한 뒤 Python으로 검사를 실행했어요. 검사 항목은 다음과 같아요.
   - 중복 턴, 턴 수 불일치, 고아 턴, 고아 FTS, 고아 벡터
   - `(session_id, turn_id)` 단위의 FTS 중복, `(session_id, turn_index, chunk_seq)` 단위의 벡터 중복
   - 고아 그래프 노드, 끊긴 엣지, `vault_path` 중복
2. 결과: 반복 sync가 남긴 중복은 없었어요. 다른 문제 두 가지를 찾았어요.
   - FTS 중복 486행과 벡터 중복 359행이 모두 claude 세션 `db1f7506-4498-4f32-8ad7-237f8d7891aa`(CrinityOLLVM, 2026-09-22) 하나에 있었어요.
   - `vault_path`가 겹치는 경우가 33건 있었고, 모두 codex 세션이었어요.
3. 중복 벡터는 모두 `embedded_at = 2026-09-23 12:42:08`로 같은 초에 생겼어요. Claude는 sync 두 개가 같은 순간에 이 세션을 처리했을 가능성이 높다고 봤어요. 이 판단은 **미검증**이에요.
4. 겹치는 `vault_path`의 세션 ID를 확인했어요. 예를 들어 `01a1330d-11b6-...`과 `01a1330d-eeed-...`가 `codex_s1_01a1330d.md`를 함께 썼어요. 파일명 생성은 `crates/secall-core/src/ingest/markdown.rs:421`의 `session.id.chars().take(8)`였어요.
5. 실제 파일을 확인했어요. vault 경로는 `C:\Users\Thurion\AppData\Roaming\secall\config.toml`의 `[vault] path`(`C:\Users\Thurion\obsidian-vault\seCall`)에서 찾았어요. `codex_s1_01a1330d.md`에는 `01a1330d-eeed-...`만 있었어요. `11b6`의 md는 덮어써져서 사라졌어요.
6. 시맨틱 엣지 추출 `extract_one_session_semantic`(`ingest.rs` 905줄 근처)이 vault md를 읽는 것을 확인했어요. 그래서 충돌한 세션 한쪽의 그래프는 다른 세션의 내용으로 만들어졌어요.
7. 파일명을 바꾸기 전에 파일명을 읽는 코드를 찾았어요. `rg -ln "\.sessions"`와 `rg "file_stem|rsplit\('_'|split\('_'\)"`를 썼어요.
   - `vault/mod.rs:38` `resolve_session_file`: 저장 경로 → legacy 경로 → 8자 prefix 탐색 순으로 찾아요. prefix가 여러 개 맞으면 ambiguous 오류를 내요.
   - `ingest/lint.rs:160`: frontmatter `session_id`를 먼저 쓰고, 없으면 마지막 `_` 뒤를 써요. 전체 UUID에는 `_`가 없어서 영향이 없어요.
   - `mcp/server.rs`의 `file_stem` 사용처는 wiki 경로라 관계가 없어요.
8. `--force` 경로(`ingest.rs` 1143-1159줄)는 기존 vault md를 지우지 않아요. 파일명이 바뀌면 예전 파일이 고아 파일로 남아요.
9. `secall ingest <세션 ID>`의 ID 조회 `find_session_by_id`(`ingest.rs` 1278줄 근처)는 `~/.claude/projects`만 찾아요. codex 세션은 원본 경로로 넘겨야 해요.

### 분석

codex 세션 ID는 UUIDv7이에요. UUIDv7의 앞 8자는 타임스탬프 상위 비트예요. 약 1분 안에 시작한 codex 세션들은 vault 파일명이 같아졌어요. 그래서 나중에 처리한 세션이 앞 세션의 md를 덮어썼어요. 69개 세션이 33개 파일을 공유했어요(32쌍 + 3개 묶음 1건).
DB의 턴은 두 세션 모두 남아 있었어요. 그래서 검색에는 영향이 없었어요. 영향은 Obsidian vault, wiki, vault 폴백 경로, 시맨틱 그래프에 있었어요.

### 처리방법 결정

Claude가 두 가지를 제안했어요. 하나는 파일명에 쓰는 ID를 늘리는 것이고, 다른 하나는 중복 세션만 정리하는 것이에요. 사용자 결정: *"2개를 같이 할께 중복세션 명령어 알려주고 vault 파일명 충돌 수정 하자"*
파일명 길이는 전체 ID를 쓰기로 했어요. Claude는 기존 파일 이름은 바꾸지 않았어요. 기존 세션은 DB의 `vault_path`를 그대로 쓰기 때문이에요.

## C. 릴리스 빌드 시간과 `release-local` 프로필 (PR #3)

사용자가 물었어요: *"그런데 이거 릴리즈 빌드는 왜이렇게 오래 걸리는거야?"*
Claude는 `Cargo.toml`의 `[profile.release]`를 확인했어요. 설정은 `lto = "fat"`, `codegen-units = 1`이에요. 그리고 `crates/secall-core/Cargo.toml`의 큰 의존성을 확인했어요. `ort`, `lindera`, `kiwi-rs`, `usearch`, `tokenizers`, `rust-embed`가 있어요.
Claude의 설명은 이랬어요. `codegen-units = 1`은 큰 크레이트를 단일 스레드로 컴파일해요. fat LTO는 링크 단계에서 전체를 다시 최적화해요. 둘 다 코드를 조금만 바꿔도 매번 다시 실행돼요.

사용자 결정: *"로컬 설치용 빠른 릴리스 프로필(release-local: thin LTO, codegen-units 16) 추가해줘"*
`[profile.release-local]`은 `inherits = "release"`, `lto = "thin"`, `codegen-units = 16`이에요. 배포용 `release`는 그대로 뒀어요.

| 항목 | `release` | `release-local` |
|---|---|---|
| 재빌드 (`secall-core/src/lib.rs` touch) | 5분 20초~6분 42초 (이 세션의 실제 빌드) | 1분 18초 |
| 첫 빌드 (새 프로필, 의존성 포함) | — | 3분 16초 |
| 바이너리 크기 | 61.7MB | 65.6MB |

`release` 숫자는 이 세션에서 코드를 바꾼 뒤 실행한 두 빌드의 시간이에요. 같은 touch 조건에서 다시 측정하지는 않았어요.
사용자 결정: *"release-local 프로필 커밋하고 PR 만들어서 머지해줘"* → PR #3을 머지했어요.

## 이 세션에서 얻은 규칙

- **codex 세션 ID(UUIDv7)의 앞 8자를 고유 키로 쓰지 않아요.** 앞 8자는 타임스탬프예요. 로그 출력용 `short_id`는 괜찮아요. 하지만 파일명이나 조회 키로 쓰면 충돌해요.
- **모든 파서는 `end_time`을 채워야 해요.** ingest는 `end_time IS NULL`을 "진행 중 세션 → 매 sync 재인제스트"로 해석해요.
- **`origin`은 upstream `hang-in/seCall`이고 푸시 권한이 없어요.** 포크 작업은 `fork` 리모트에 푸시하고, `Crinitys/seCall`에 PR을 만들고, `--merge`로 머지해요. (영속 메모리에 기록)
- **로컬 설치는 `cargo build --profile release-local -p secall`을 써요.** 결과물은 `target/release-local/secall.exe`예요.
- **vault 파일명 규칙을 바꾼 바이너리는 설치한 뒤에 재인제스트해요.** 이전 바이너리로 재인제스트하고 예전 파일을 지우면 md가 사라져요.
- **`secall.exe`를 교체하기 전에 `secall mcp`를 잡고 있는 프로세스를 확인해요.** 화면에 없는 고아 `claude.exe`가 잡고 있을 수 있어요.
