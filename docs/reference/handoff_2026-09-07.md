ingest 된다"는 작은 신고에서 시작해 MCP·Web UI·그래프·VRAM·검색 품질까지 연쇄적으로 파고든

## 1. 발단 — 옵저버 세션 ingest

**문제**: `secall ingest --auto` 가 `~/.claude/projects` 를 훑을 때, claude-mem 플러그인이
만든 옵저버 세션 폴더(`C--Users-Thurion--claude-mem-observer-sessions`)까지 실사용자 대화와
함께 인덱싱하고 있었다.

**탐색 과정**:

1. 처음엔 해당 폴더명을 `is_pruned_dir` 에 하드코딩하려 했다 (`subagents`/`.git`/
   `node_modules` 와 같은 자리).
2. 사용자 판단으로 방향 전환 — 특정 사용자 경로를 코드에 박는 것은 부적절. 홈 디렉터리
   prefix + `claude-mem` 조합으로 일반화하는 안도 검토했으나, 여전히 코드가 특정 플러그인을
   아는 문제가 남았다.
3. 최종: **설정 기반**으로 일반화하고 `secall init` 에서 프롬프트로 받는다.

**해결**: `config.ingest.exclude_patterns: Vec<String>`. 디렉터리명에 이 문자열이 포함되면
walkdir 에서 서브트리째 prune. `find_claude_sessions_excluding()` 을 새로 만들어
`ingest --auto` / `sync` 양쪽에 적용. `secall init` Step 7 에서 쉼표 구분으로 입력받는다.

**교훈**: "지금 내 환경의 문제"를 코드에 박지 말고 설정으로 올리면, 같은 종류의 다른 문제
(다른 플러그인, 다른 봇 폴더)까지 사용자가 스스로 처리할 수 있다.

## 2. MCP 기동 시 Web UI 자동 실행 — 그리고 그것이 만든 사고

**요구**: `secall mcp` 를 켤 때마다 `secall serve` 를 따로 띄우는 게 불편하다. 단, Web UI 는
`web-ui` feature 컴파일 여부에 따라 달라지니 지원하는 빌드에서만 켜야 한다.

**1차 구현**: `#[cfg(feature = "web-ui")]` 로 감싸고 `tokio::spawn` 으로 `serve::run` 을
백그라운드 기동. `config.web.auto_start` / `config.web.port` (기본 `true`/`8080`) 추가.
포트 충돌이 잦은 8080 을 배려해 `AddrInUse` 시 10씩 올려 최대 30회 재시도.

**사고**: 배포 후 사용자 신고 — *"세션별로 mcp 가 켜지면서 웹도 mcp 갯수만큼 열어버리고
있어."*

MCP 서버는 Claude Code **세션마다 프로세스가 뜬다.** 포트 재시도 로직이 오히려 독이 되어
세션 N개 → 8080, 8090, 8100 … 으로 웹 서버가 N개 열렸다.

**탐색**:

- 1안: 재시도 없이 고정 포트 1회만 바인딩 → 먼저 뜬 인스턴스만 웹을 잡고 나머지는 스킵.
  포트 자체가 mutex 역할. **문제**: 무관한 프로그램이 8080 을 점유하면 웹이 영영 안 열린다
  (사용자가 즉시 지적).
- 2안: 점유자가 secall 인지 HTTP 로 판별해서 분기. secall 이면 스킵(중복 방지), 남의 앱이면
  다음 포트로. **채택**.

**판별 방법 선정**: 처음엔 `/api/status` 를 쓰려 했으나 이 엔드포인트는 DB 락을 잡고 통계를
계산한다 — probe 용으로 부적합. 사용자 제안대로 **전용 엔드포인트**를 신설했다.

**해결**:

- `GET /api/info` 신규 — `{"name":"secall","version":"..."}` 만 반환, DB 접근 없음.
- `start_rest_server(single_instance: bool)`. `single_instance` 면 `AddrInUse` 시
  `/api/info` 를 700ms 타임아웃으로 GET 해서 `name == "secall"` 이면 기동 생략, 아니면
  포트 +10 재시도(최대 30회).
- `secall serve`(수동)는 `single_instance=false` — 사용자가 명시적으로 띄우는 것이므로
  생략 규칙을 적용하지 않는다.

**실동작 검증**: MCP 를 2개 띄워 두 번째가 "다른 secall 인스턴스가 이미 Web UI 서비스 중 —
기동 생략" 을 남기고, 8080 에 리스너가 하나만 남는 것을 확인.

**트레이드오프(의도적 미해결)**: 웹을 잡은 리더 세션이 종료되면 웹 서버도 함께 죽고, 이미
떠 있는 다른 세션들은 시작 시점에만 시도했으므로 넘겨받지 않는다. 주기적 재바인딩 루프를
넣을 수 있으나 복잡도 대비 이득이 적다고 판단해 보류.

## 3. 포크 버전 체계 도입

**요구**: 버전 문자열에 포크·나이틀리·시퀀스를 넣고 싶다.

**탐색** — 실제 프로젝트 관례 조사:

| 프로젝트 | 표기 | 방식 |
|---|---|---|
| rustc | `1.90.0-nightly (a1b2c3d 2026-09-06)` | **다음** 버전 + `-nightly` |
| Node.js | `v25.0.0-nightly20260906abc1234` | 다음 메이저 + 날짜/해시 |
| Neovim | `v0.11.0-dev-1234+gabc1234` | 다음 버전 + 커밋수 + 해시 |
| LibreWolf(포크) | `128.0-2` | 업스트림 + 포크 리비전 |
| Debian | `1.2.3-1ubuntu2` | 업스트림 + 배포자 리비전 |
| VSCodium(포크) | 업스트림 버전 그대로 | 포크는 **이름**으로 구분 |

**핵심 통찰 2가지**:

1. 나이틀리는 "다음 버전"에 프리릴리즈를 붙인다. stable 1.89 면 nightly 는 1.90.0-nightly.
   이러면 SemVer 상 `-` 접미사가 낮게 정렬되는 문제가 자연히 해소된다.
2. 포크 이름은 보통 버전이 아니라 제품명에 넣지만, Debian 식 접미사 리비전도 관례다.

**선정**: `0.8.0-crinity.nightly.N`. 정렬이
`0.7.0(upstream) < 0.8.0-crinity.nightly.N < 0.8.0` 으로 맞다.

## 4. 빌드 시간 — fastrel 프로파일 (추가 후 되돌림)

32코어인데 release 빌드가 5분 30초 걸리는 것을 조사했다.

- **크레이트 단위 병렬**: cargo 기본 `-j32` 로 의존성 300여 개는 잘 병렬화됨.
- **크레이트 내부**: `[profile.release]` 의 `codegen-units = 1` + `lto = "fat"` 때문에
  secall 자체 코드젠과 최종 LTO 가 사실상 단일 스레드. 이게 병목.

`[profile.fastrel]`(inherits release, `lto = "thin"`, `codegen-units = 16`)을 추가해 실측:

| | fat (release) | thin (fastrel) |
|---|---|---|
| 빌드 | 330초 | **162초** |
| 바이너리 | 61.7MB | 65.6MB |

**되돌린 이유**: 사용자 판단 — seCall 은 형태소 분석(lindera/kiwi), 벡터 SIMD 스캔, 그래프
알고리즘 등 실제 CPU 핫패스가 있어 런타임 성능이 중요하다. 빌드 시간보다 성능을 택했고,
쓰지 않을 프로파일을 남기지 않기 위해 revert 커밋으로 제거했다(`d29464d`).

**thin vs fat 정리** (설명 요청으로 정리한 내용):

- fat: 모든 크레이트 IR 을 하나의 거대 모듈로 병합 후 통째로 최적화. 전역 시야라 인라이닝·
  dead code 제거가 최대치. 병합된 단일 모듈이라 병렬화가 거의 안 됨.
- thin: 모듈을 분리한 채 요약(summary) 인덱스만 만들어 필요한 함수만 크로스 모듈 임포트.
  병렬 처리 가능, fat 성능의 대부분을 훨씬 싼 비용에 얻음.

## 5. CI 가 막힌 두 가지

### 5.1 pnpm 9 vs 12 — overrides 위치 이동

로컬 pnpm 12 는 `package.json` 의 `pnpm.overrides` 를 더 이상 읽지 않는다. 이걸
`pnpm-workspace.yaml` 로 옮겼더니 CI(pnpm 9)가 `ERR_PNPM_LOCKFILE_CONFIG_MISMATCH` 로
실패했다.

해당 override 는 장식이 아니라 **보안 픽스**였다 — `@ungap/structured-clone` CVE-CWE-502
(deserialization) 대응으로 1.3.1+ 를 강제하는 것. git log 로 도입 경위를 확인하고 lockfile 의
핀이 유지되는지까지 확인한 뒤 CI 의 pnpm 을 12 로 올려 해결했다.

`pnpm-workspace.yaml` 최종:

```yaml
packages: [.]
overrides:
  '@ungap/structured-clone': ^1.3.1
allowBuilds:
  esbuild: true
```

### 5.2 `RUSTFLAGS: "-Dwarnings"`

`vector.rs:192` 의 clippy 경고(`useless_borrows_in_formatting`)를 "기존 코드라 무관"으로
넘겼는데, CI 는 `-Dwarnings` 라 **에러로 승격**되어 빌드가 깨졌다.

**교훈**: 로컬 검증은 CI 와 동일한 조건으로 해야 한다. 이후 모든 검증을
`RUSTFLAGS="-Dwarnings" cargo clippy --workspace --all-targets` + `cargo fmt --check` +
전체 테스트로 통일했다.

## 6. 턴 0개 세션 파일 — error 인가 skip 인가

**증상**: `sync` 마다 WARN 5줄 + `5 errors`.

```text
WARN failed to parse session file ... claude session has no parseable turns: ...
```

**조사**: 해당 jsonl 을 파싱해보니 **JSON 은 전부 정상**(파싱 실패 0건)이고, 내용이
`queue-operation` / `attachment` / `system` / `last-prompt` / `mode` / `permission-mode` /
`bridge-session` 같은 메타 이벤트뿐 — `message.role` 이 하나도 없다. 세션을 열기만 하고
대화를 하지 않은 파일이다.

**판단**: 파서의 `turns.is_empty()` 가드 자체는 의도된 동작(#138)이지만, **손상 파일이 아니라
인제스트할 내용이 없는 파일**이므로 error 로 세는 것이 과하다.

**해결**:

- `SecallError::NoTurns { path }` 신규. 파서 4종(claude/codex/gemini/opencode)이 이 타입을
  반환.
- `ingest_path` 가 `is_no_turns()` 로 판정해 `skipped` 로 집계하고 로그를 debug 로 낮춤.
- 판정은 `SessionParser::parse` 가 `SecallError::Parse { source }` 로 감싸는 것을 고려해
  bare/wrapped 양쪽을 확인한다.

**범위 판단**: ZIP export 계열(`parse_all` 경로 — ClaudeAi/ChatGpt/GeminiWeb)은 "턴 없음"
에러를 내지 않으므로 대상이 아니다. 범위를 넓히지 않았다.

**검증**: 회귀 테스트 2건(파서가 NoTurns 반환 / 래핑 통과 판정) + 실제 sync 에서
`5 errors → 0 errors`, WARN 소멸 확인.

## 7. 그래프가 자동으로 안 채워지던 이유 (훅 상호작용 버그)

**신고**: *"sync --local-only 를 실행해도 그래프를 안 만든다."*

**조사 경로**:

1. graph 트리거 지점을 전수 조사 — 자동 스케줄러는 없고 4경로뿐:
   `ingest --auto-graph`(기본 **꺼짐**), `sync`(기본 켜짐), `graph build`(수동),
   `graph semantic`/`rebuild`(수동, LLM).
2. `sync.rs:363` 의 조건 발견:

   ```rust
   if !no_graph && !ingest_result.new_session_ids.is_empty() {
   ```

   **그 실행에서 새로 ingest 된 세션이 있을 때만** graph 단계가 돈다.
3. DB 84 세션 vs 그래프 78 세션 = 6개 차이. sync 가 넣었다면 그래프에도 있어야 하는데 없다
   → 다른 경로로 들어왔다는 뜻.
4. `~/.claude/settings.json` 확인:

```text
   SessionEnd   : secall ingest --auto --cwd $PWD      ← --auto-graph 없음
   SessionStart : secall sync --local-only
   ```

**근본 원인**: SessionEnd 훅의 `ingest --auto` 가 새 세션을 **먼저 가져가고** 그래프엔 안
넣는다. 다음 세션 시작 시 sync 는 그 세션을 이미 인덱싱된 것으로 보고 skip →
`new_session_ids` 가 비어 graph 단계를 통째로 건너뛴다. **훅 두 개가 서로 발목을 잡는 구조.**

**해결**: SessionEnd 훅에 `--auto-graph` 추가.

**추가 발견 — cross-session 엣지 부재**: 그래프에 `same_project`/`same_day` 엣지가 **0개**
였다. 증분 추출(`extract_for_sessions`)은 구조상 이 엣지를 만들 수 없다(전체 vault 순회 필요).
코드 주석에도 "사용자는 주기적으로 `secall graph build` 를 실행해야 한다" 고 명시돼 있다.
즉 세션이 파일·토픽으로만 뻗어 있고 **세션끼리는 연결이 없는 상태**였다.

**결과**: `graph build` 실행 후

- 세션 노드 78 → **84** (누락 6개 편입, 진단과 정확히 일치)
- `same_project` 55, `same_day` 59, `by_agent` 6, `belongs_to` 6 신규 생성

`same_project` 가 55개뿐인 이유는 정상 — 코드가 전체 조합(clique)이 아니라 프로젝트별
시간순 정렬 후 **인접한 것끼리만** 연결한다(`group.windows(2)`). 43개 세션이면 42개 엣지.
clique 였다면 900개 넘게 생겨 그래프가 못 쓰게 된다.

## 8. VRAM — 이 세션의 가장 큰 발견

**배경**: 사용자 환경은 RTX 3080 Ti 12GB 인데 상시 7~8GB 를 다른 프로그램이 쓴다. LLM 에
쓸 수 있는 건 사실상 3GB 남짓.

### 8.1 첫 오판과 정정

MCP 검색을 하이브리드로 바꾸면 임베딩 모델이 매번 로드되는데, 필자는 "0.6B 모델이니 ~1GB,
걱정할 규모가 아니다" 라고 안내했다. 사용자가 "RAM 에 로드돼 엄청 느려질 것 같다" 고 우려를
표해 실측했더니:

```text
qwen3-embedding:0.6b: VRAM 5509MiB, ctx=32768
```

**가중치는 640MB 인데 Ollama 가 컨텍스트 32768 기준으로 KV 캐시를 통째로 선할당해 5.5GB 를
먹고 있었다.** 사용자의 직감이 맞았고 필자의 추정이 틀렸다.

### 8.2 원인과 해결

secall 이 임베딩 요청에 `num_ctx` 를 보내지 않아 모델 기본 컨텍스트가 적용되고 있었다.

| num_ctx | VRAM |
|---|---|
| 32768(기본) | 5509MiB |
| **4096** | **2261MiB** |

`config.embedding.ollama_num_ctx`(기본 4096)를 추가하고 `EmbedRequest.options.num_ctx` 로
전달. **이건 검색만이 아니라 ingest 전체에 적용되는 개선** — 세션 임베딩할 때마다 5.5GB 를
잡고 있었기 때문.

### 8.3 안전성 검토 — 4096 이면 잘리지 않는가

사용자 질문: *"Compact 를 안 하면 4096 도 부족하지 않나?"*

코드로 확인:

- 임베딩 입력은 `chunk.text` 만 사용(`vector.rs:128`). `context` 필드는 붙지 않는다.
- 턴 단위로 나눈 뒤 다시 청킹하므로, 세션이 아무리 길어도 한 번의 임베딩 입력은
  **턴 하나의 청크 하나**.
- `split_into_chunks` 는 **문자 단위**(`text.chars()`)로 최대 3600자.

최악(1자=1토큰)이어도 3600 < 4096. **세션 길이·compact 여부는 청크 개수만 늘릴 뿐 개별 입력
크기에 영향이 없다.**

**단 하나의 예외**: `wiki vectorize` 는 페이지를 청킹하지 않고 **통째로** 임베딩한다
(`indexer.rs`: `self.embedder.embed(&content)`). 여기에 4096 을 적용하면 긴 페이지가 조용히
잘린다. → **wiki vectorize 만 모델 기본 컨텍스트를 쓰도록 예외 처리.** config 주석에
"청크 상한을 늘린다면 이 값도 함께 올려야 조용한 truncation 을 피한다" 를 남겼다.

### 8.4 graph LLM 도 같은 문제 — 그런데 함정이 있었다

`graph/llm.rs` 의 `ollama_chat` 도 `options` 에 `temperature` 만 보내고 `num_ctx` 가 없었다.
입력은 `BODY_LIMIT = 8000` 바이트로 이미 제한돼 있어 4096 이면 충분하다고 판단하고 추가했다.
**그런데 모델 벤치를 돌려보니 4096 이 오히려 graph 를 망가뜨렸다** (§9).

## 9. 모델 벤치마크 — 진짜 원인은 모델이 아니라 `think`

**동기**: graph LLM 기본값 `gemma4:e4b` 를 더 작은 모델로 바꿔 VRAM 을 아낄 수 있는지.

**방법**: secall 의 실제 `SYSTEM_PROMPT` / `build_user_content` / `BODY_LIMIT` 을 그대로
재현한 파이썬 벤치를 만들고, 사용자의 실제 세션 md 를 입력으로 모델별 비교(스크립트는
scratchpad, 저장소에는 넣지 않음). 채점은 secall 과 동일하게 허용 relation 통과율로.

**1차 결과 — 전부 실패**:

| 모델 | thinking | content | 문제 |
|---|---|---|---|
| gemma4:e4b | 2501자 | **0자** | 추론이 num_ctx 를 소진해 출력 없음 |
| qwen3:4b | **16370자** | 산문 설명 | 프롬프트 미준수 |
| qwen3:1.7b | 1282자 | JSON 배열 | 봉투가 `[...]` (secall 은 `{"edges":[...]}` 요구) |

**핵심 발견**: 셋 다 thinking 모델이고, secall 이 `think` 파라미터를 보내지 않아 추론이 켜진
채 돌고 있었다. 즉 **`graph.num_ctx = 4096` 을 단독으로 넣었다면 graph semantic 이 조용히 빈
결과를 내게 되는 회귀를 배포할 뻔했다.**

**2차 — `think: false` 적용**:

| 모델 | 결과 |
|---|---|
| **gemma4:e4b** | 10.3s, 마크다운 펜스로 감싼 `{"edges":[...]}` → secall 이 펜스 제거 후 파싱 가능 ✅ |
| qwen3:4b | 30s, 추론이 content 로 새어나옴 ❌ |
| qwen3:1.7b | 6.2s, 배열 봉투 ❌ |

**결론**: 모델을 바꿀 필요가 없었다. 기본값 `gemma4:e4b` 가 최선이고, 필요한 건
`think: false` 한 줄이었다. 효과는 세 가지 — 빈 응답 해소, 응답 시간 3배→1배, JSON 파싱 안정.

**부수 확인**: thinking 미지원 모델(qwen2.5:0.5b)에 `think: false` 를 보내도 정상 수용되는
것을 실측해, 방어적 폴백 코드를 넣지 않았다.

**VRAM 실측(gemma4:e4b)**: ollama 자체 보고는 3077MiB(4096) vs 3137MiB(65536)로 60MiB 차이
지만, **GPU 실제 증가분은 4451MiB vs 5470MiB 로 약 1GB 차이**. CUDA 컨텍스트·컴퓨트 버퍼가
따로 잡히기 때문. 절대값 4.4GB 는 3GB 예산에는 여전히 초과 → 훅에서는 semantic 을 빼는
전략을 유지한다.

**참고**: `gemma4:e4b` 는 다운로드 9.6GB 이지만 MatFormer(effective 4B) 구조라 실제 로드는
3GB 대다. 파일 크기로 VRAM 을 추정하면 안 된다.

## 10. 모델 동시 로드 방지

**요구**: *"embed 나 graph 처럼 llm 을 호출할 일이 있을 때 절대로 2개 이상의 모델이 동시에
로드되면 안 된다. 가장 중요한 건 로드할 때 정확한 모델이 지정되어야 한다는 것."*

### 10.1 발견한 버그

`unload_embedding_model_if_needed` 의 가드가

```rust
if config.embedding.backend != "ollama" || config.graph.semantic_backend != "ollama" { return; }
```

— **graph 백엔드까지 ollama 일 것을 요구**했다. 사용자 설정은 `lmstudio` 였으므로 언로드가
**아예 발사되지 않았고**, Ollama 임베딩 모델과 LM Studio 의 LLM 이 동시에 올라갈 수 있었다.

### 10.2 정리한 설계

**불변식: 다른 모델을 올리기 직전에 기존 모델을 내린다.**

| 경로 | 처리 |
|---|---|
| ingest: embed → semantic | 임베딩 내림 → LLM → **LLM 내림** |
| graph rebuild (취소 경로 포함) | 임베딩 내림 → LLM → LLM 내림 |
| wiki update (sync 가 자동 호출) | 임베딩 내림 → LLM → LLM 내림 |
| MCP/REST/CLI 검색 | **warm 유지** (LLM 경로가 어차피 먼저 내림) |
| log / wiki vectorize / embed --all | 수동이라 제외 |

- 중복 언로드 코드를 `unload_ollama_model(url, model, reason)` 하나로 통합.
- **모델명 정합성**: 로드와 언로드가 같은 config 표현식
  (`config.X.ollama_model.unwrap_or(DEFAULT_상수)`)으로 이름을 구한다. 하드코딩 문자열을
  상수로 교체해 어긋날 여지를 없앴다.
- 검색을 warm 으로 둔 근거(실측): 콜드 3332ms vs 웜 1306ms — 매 검색마다 2초를 잃는다.
- 임베딩을 쓰는 경로를 전수 조사한 결과, warm 이 필요한 것은 전부 `SearchEngine::embed_query`
  하나를 공유한다(MCP recall / MCP wiki_search semantic / REST / CLI recall). 별도로 챙길
  것이 없다.

### 10.3 남은 케이스 — 정직한 감사

실제로 재현했다. LLM 이 올라간 상태에서 다른 프로세스가 검색하면:

```text
qwen3-embedding:0.6b  2261MiB
gemma4:e4b            3077MiB      → 로드된 모델 수: 2
```

**프로세스 간에는 협조적 언로드가 무력하다.** "내가 올리기 전에 남을 내린다"는 되지만
"남이 나중에 올리는 것"은 못 막는다. 완전 해결은 `OLLAMA_MAX_LOADED_MODELS=1` 뿐이다.

**사용자 판단으로 미해결 유지**: VRAM 이 빠듯한 상황은 자리를 비웠을 때이고 그때는 훅만
도는데 훅은 LLM 을 아예 안 부른다. 수동 LLM 배치는 VRAM 여유 있을 때만 실행하며 그때는
2개(6.6GB)가 올라가도 들어간다. **위험 조합(VRAM 부족 + 2개 로드)이 성립하지 않는다.**

## 11. 검색 — MCP 가 CLI 보다 낮은 품질이었다

**발단**: 사용자 질문 — *"안 쓰는 검색 방식이 있나? 그래프 검색은 쓰이나?"*

**조사 결과**:

| 방식 | 사용처 |
|---|---|
| BM25 / 벡터 | 전부 |
| **하이브리드 RRF 융합** | ⚠️ **CLI `secall recall` 에서만** (`recall.rs:98` 유일 호출) |
| 그래프(관련 세션) | MCP recall 응답의 `related_sessions` — 자동(Adamic-Adar) |
| 그래프 탐색 | MCP `graph_query` — 명시 호출 |
| temporal | 검색이 아니라 날짜 필터 |

`do_recall`(MCP)과 REST 는 쿼리 타입별로 따로 검색해 **결과를 이어붙이고 score 로 정렬**만
했다. BM25 는 정규화(0~1), 벡터는 `1.0 - distance` 라 스케일 파탄까지는 아니지만, 순위 기반
융합(RRF)이 점수 직접비교보다 견고하다.

**정정한 오판**: 처음엔 "REST/웹도 함께 개선된다"고 했으나, `RestRecallParams` 는 `QueryItem`
을 **1개만** 만들어 단일 모달리티만 돈다. 융합이 발동할 수 없다. 사용자에게 정정 보고했다.

**해결**:

- `RRF_K` 공개, `do_recall` 이 결과를 모달리티별로 수집 → `reciprocal_rank_fusion` 으로 융합.
- 후보를 `limit * 3` 까지 조회(RRF 는 순위 기반이라 후보가 얕으면 효과가 없다 — CLI 와 동일).
- `sort_and_dedup()` — 융합 전 모달리티별 순위 확정 + `(session_id, turn_index)` 중복 제거.
  중복이 남으면 그 turn 의 RRF 기여가 이중 계산된다.
- **하이브리드 기본화**: temporal 을 뺀 모든 쿼리를 BM25/벡터 양쪽에 태운다. 호출하는 모델이
  keyword 만 보내도 하이브리드가 되도록. MCP 툴 설명도 "Every query runs hybrid search" 로
  수정.
- **임베딩 실패는 BM25 폴백** — 하이브리드를 상시화하면서 필수가 된 안전장치. Ollama 가
  꺼져 있어도 검색이 깨지지 않는다.

## 12. `secall init` 개선

- **Step 7**: ingest 제외 경로 패턴(§1)
- **Step 8**: Knowledge Graph 시맨틱 백엔드 선택 — 코드 기본값이 `ollama_cloud` 라 API 키
  없이는 동작하지 않는데 init 이 묻지 않아 로컬 사용자는 설정을 직접 편집해야 했다.
  로컬 `ollama`(권장) / `disabled` / `ollama_cloud` 중 선택.
  - 백엔드 전환 시 `graph.ollama_model` 을 **비운다** — 이전 백엔드용 모델명이 남으면
    존재하지 않는 모델을 호출한다(실제로 lmstudio 모델명이 ollama 로 넘어갈 뻔한 사례).
  - `ollama` 선택 시 모델 준비 명령과 VRAM 운용법을 안내.
- `num_ctx` / `web` 등 나머지 권장값은 코드 기본값이라 `config.save()` 가 자동 기록한다.

## 13. 최종 설정

### 훅 (`~/.claude/settings.json`, 백업 `settings.json.bak`)

```text
SessionStart : secall sync --local-only --no-semantic
SessionEnd   : secall ingest --auto --cwd $PWD --auto-graph --no-semantic
```

- `--auto-graph`: 신규 세션을 즉시 그래프에 편입(규칙 기반, LLM 불필요)
- `--no-semantic`: 훅에서 4.4GB LLM 을 절대 올리지 않음

### config (`%APPDATA%\secall\config.toml`, 백업 `config.toml.bak`)

```toml
[ingest]
exclude_patterns = ["claude-mem"]

[embedding]
ollama_num_ctx = 4096          # 5.5GB -> 2.2GB

[graph]
num_ctx = 4096
semantic_backend = "ollama"    # lmstudio -> ollama, ollama_model 제거(기본 gemma4:e4b)

[web]
auto_start = true
port = 8080
```

### 수동 운용

```text
secall graph build                    # 가끔 — cross-session 엣지 갱신, LLM 불필요
secall graph rebuild --retry-failed   # VRAM 여유 시 — semantic_extracted_at IS NULL 만 처리
```

## 16. 다음 세션을 위한 메모

1. **upstream 반영 여부 미정.** 이 세션의 개선 중 `NoTurns` skip, `num_ctx` 제어,
   `think:false`, MCP 하이브리드 RRF, `/api/info` 는 포크 특수성이 없어 upstream PR 감이다.
   포크 버전 체계(`Cargo.toml` version)만 제외하면 된다.
2. **Web UI 리더 승계 미구현** (§2 트레이드오프). 웹을 잡은 세션이 죽으면 새 세션이 뜰
   때까지 웹이 없다.
3. **`graph build` 출력이 오해를 부른다.** 재실행 시 "114 edges created" 로 표시되지만
   `INSERT OR IGNORE` 라 실제 증가는 없다. 시도 횟수가 아니라 실제 삽입 수를 세도록 고치면
   좋다.
4. **REST `/api/recall` 은 여전히 단일 모달리티.** `mode: "hybrid"` 를 추가하면 웹 UI 도
   융합 검색을 쓸 수 있다.
5. **`log` / `wiki vectorize` / `embed --all` 은 모델 언로드 대상에서 제외**되어 있다
   (수동 명령이라는 판단). 자동화한다면 언로드를 함께 넣어야 한다.
6. 벤치 스크립트는 scratchpad 에만 있고 저장소에 없다. 모델 재평가가 필요하면 §9 의 방법
   (실제 SYSTEM_PROMPT + 실제 세션 md + 허용 relation 통과율)을 재현하면 된다.
